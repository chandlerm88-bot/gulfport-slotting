Re-slotting is different. It throws the layout away and works out a new one from scratch, so every item can end up somewhere else, for everyone on this plan. Worth doing when the range changes seasonally or the aisles are re-configured — not day to day.

Layout & pick path

Lanes run front-to-back down each column. Split is how many positions are reached from the near face — the rest are picked from the far side, so nothing gets buried. Set split to the full depth for a block you can only reach from one side.

The percentages place each block on the floor plan, measured from the top-left corner of the building.
A picker walks the corridors, not the blocks, and a corridor with product on both sides is picked left and right on one trip — that is where the volume should sit. A corridor with product on one side is walked in and back out, so it earns twice the steps for the same faces and should hold whatever moves least.

Yield is faces reached per 1% of the building walked, doubled against one-sided corridors for the trip back. The route is ranked by it unless you reorder.

Order also sets the pallet build: trays carry load down the can columns and go first, cartons and carriers put it through board and go last.
Derived from the item name, then checked against the packaging dimensions.

Shared sync

Connected to . Nothing to set up — just put your name in so the activity log shows who did what.
Everyone pointing at the same project sees the same plan. Paste the project URL and the publishable key from Supabase → Project settings → API Keys — the legacy anon key works too. Never the secret or service_role key. They stay on this device; the plan itself lives in the table.
Run this once in the Supabase SQL editor:

create table if not exists rb_plan (id text primary key, payload jsonb, rev int default 0, updated_by text, updated_at timestamptz default now());

alter table rb_plan enable row level security;
drop policy if exists rb_all on rb_plan;
create policy rb_all on rb_plan for all using (true) with check (true);

do $$ begin
  alter publication supabase_realtime add table rb_plan;
exception when duplicate_object then null;
end $$;

That last block is what makes one person's edits appear on someone else's screen without a refresh. Safe to run more than once.
